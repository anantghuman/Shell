(2) Explain how you communicated the return value of the 
    child to the parent. What feature of wait() did you use?

    WEXITSTATUS() to get the value that the child originally passed to exit().

(1) In the provided utility function signal_action(), what does the call to
  sigaction() do?  Why was sigaction() used instead of signal()?

    The call to sigaction changes what the process does when the given
    signal is recieved to the handler that is passed in. In part 1, we
    use a function* as the handler. Sigaction() was used instead of
    signal() because it does not allow the signal being changed to be
    recieved while the handler is being executed. Sigaction() also
    allows you to keep track of the previous handler in case it needs
    to be reset or used elsewhere. Lastly, it allows flags to be set
    like SA_RESTART which makes certain system calls automatically
    restart if they are interrupted by the signal while the handler is running.

(1) Describe how your implementation ensures that concurrent
    commands are executed concurrently instead of one after 
    another.

    The way that our implementation ensures that concurrent commands are
    executed concurrently is by first running all commands. If the were
    expected to be ran concurrently, we call wait() once per command.
    By doing it this way, we can ensure that the parent process only
    begins to wait for them after they all begin running concurrently.
    We only consider this case if the commands are expected to be run
    concurrently.

(2) One potential strategy for redirecting output is to run 
    the following code:

  ```
  FILE* output = fopen(filename, "w");
  stdout = output;
  stderr = output;
  ```

  This causes everything that would normally be written to 
  `stdout` to instead be written to the file described by 
  filename. Unfortunately, this strategy does not work for 
  output redirection in utcsh. More generally, it does not
  work any time fork-and-exec is used and we want to 
  redirect the output of the child process.

  Explain why this technique does not work when used in 
  conjunction with fork-and-exec, and why the dup2() 
  technique does not suffer the same issue.

    This would cause issues because "output" is just a pointer to
    a FILE struct, so when the process gets overwritten when exec() is
    called, the output pointer gets destroyed and set back to
    its original file descriptors (stdout and stderr) instead of the
    file that we want to write to. The reason dup2() works is because 
    it uses kernel-level output redirection, so the file descriptors
    are inherited even when fork() and exec() are called.
